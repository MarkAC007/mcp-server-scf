# Tool scope — what is in the MCP, what is deferred, what stays out

The SCF Controls Platform exposes 346 HTTP operations. This server deliberately wraps a subset. This page records the policy that decides which, the verdict for every operation, and the cost of the surface as it stands, so that the next endpoint the platform adds gets a recorded decision rather than a reflexive tool.

Source of truth: [`tool-scope.json`](tool-scope.json) (the verdict map) joined with the live OpenAPI spec and `src/tools/*.ts` by [`scripts/api-coverage.mjs`](../scripts/api-coverage.mjs). The table at the bottom is generated; edit the JSON, not the table.

```
node scripts/api-coverage.mjs --write            # regenerate the table from http://localhost:8000/openapi.json
node scripts/api-coverage.mjs --spec spec.json   # or from a saved spec
node scripts/api-coverage.mjs --check            # pre-merge: fail if the table is stale or the map disagrees with the code
```

The script exits non-zero when an operation has no verdict, a verdict names an operation the spec no longer has, an `in` operation has no tool, or an `out`/`deferred` operation does. A platform release that adds an endpoint, or a PR that adds a tool, therefore forces a decision here. It also checks the hand-copied vocabularies (`VOCABULARIES` in the script) against the spec's `^(a|b)$` patterns and refreshes `tests/fixtures/platform-vocabularies.json` with `--write`. The check needs a platform spec, which the platform does not publish as an artifact, so it is not wired into `ci.yml`: run it locally against a spec generated from the platform checkout before merging tool or vocabulary changes.

One limit to know about: a verdict may carry `tools: [...]` for the handful of tools that pick their route at runtime (`scf_list_vendor_action_items`, `scf_mark_notifications_read`, `scf_list_assessment_objectives`). The script checks that a tool of that name is registered, not that it calls the declared route — `tests/handlers.test.ts` covers that for the route-switching tools.

## The admission tests

An operation becomes a tool only when all four hold.

1. **Reachable with an org-scoped user API key.** That is the only credential this server holds. The platform freezes a user API key to one organisation and one role (`viewer`, `editor`, `admin`) and resolves it with no consultant relationship, no platform-admin session and no browser session. Anything gated on those is unreachable by construction, not by choice.
2. **Recurring or bulk GRC work.** The tool is something an agent does repeatedly or across many records: scoping, evidence tracking and review, tasks, risk scoring, vendor risk, accountability, audit engagement. A one-time configuration act does not earn a slot, however easy it would be to wrap.
3. **Works over a text transport.** JSON in, JSON out. Multipart uploads, pre-signed URLs, byte streams and browser redirects do not fit MCP's content model; evidence files reach the platform through collectors and the HMAC inbox, not through an assistant.
4. **Not identity, credential, billing or infrastructure administration.** Membership, invites, API keys, organisation lifecycle, storage configuration, catalog import, database and queue operations. These are decisions a person makes in the UI, and an agent holding them widens the blast radius of a single bad tool call far beyond the value of automating them.

Bulk endpoints (`…/batch`, `bulk-scope`, `bulk-unscope`, `refresh-stale`) are preferred over their single-row equivalents whenever the platform offers both: they respect the platform's write rate limit (20 writes/min per key) and they are what "daily GRC work" looks like at scale.

## The three verdicts

| Verdict    | Meaning                                                                                                                                            |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `in`       | Wrapped by at least one tool. The table names the tool.                                                                                            |
| `deferred` | Passes the four tests but is rare enough that it does not earn a slot today. Each row names the trigger that promotes it. Ask, and it gets added.  |
| `out`      | Fails at least one test. Each row carries one reason from the vocabulary below. Changing an `out` verdict means changing the policy, not the list. |

### Reason vocabulary for `out`

| Reason             | Definition                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `auth-unreachable` | An org-scoped user API key cannot reach it: platform-admin session, consultant relationship, OIDC, HMAC signature, Stripe signature.       |
| `identity-admin`   | Membership, invites, API keys, organisation lifecycle — access decisions a person makes in the UI.                                         |
| `infra-admin`      | Evidence storage, catalog import and upgrade, database, task queues, integrations — operator work.                                         |
| `binary-transport` | Multipart uploads, byte streams, pre-signed URLs.                                                                                          |
| `ui-only`          | Exists to serve a web page: per-user preferences, page-load bulk exports, form feedback, scores the UI assembles from data it already has. |
| `deprecated`       | The platform marks it a deprecated alias of an operation that is already `in`.                                                             |
| `covered`          | An existing tool already serves the need through another route or parameter; the row names it.                                             |
| `public`           | Unauthenticated; not organisation work.                                                                                                    |
| `destructive`      | Deletes or withdraws a record. New delete routes are not wrapped; removal stays a human decision in the UI.                                |

## Where the line fell

- **In:** evidence tracking single and batch, evidence tasks, file review, evidence health and frequency checks, AI-assessment review queue and decisions, windowed assessment refresh and review; bulk unscope by framework; system evidence capabilities; catalog domain and evidence definitions; risk scoring updates, control↔risk traceability, the risk profile; vendor certifications, action items and compensating controls; business functions, teams, rosters and team accountability (single and batch); user assignments and comments; notification acknowledgement; the organisation work queue; the SCRMS programme record (#1120) — obligation basis, materiality, target maturity and procedure links on scoped controls, risk acceptance with an approver, standards exceptions, deficiencies, organisation compensating controls, control validation, posture snapshots, capability tests, and the organisation profile and maturity targets in settings.
- **Deferred:** whole-org scope reset, hard deletes of scoped controls, systems and vendors, vendor-assessment edits, seat promotion on a team, comment edit/delete/history, assessment version history, risk-profile threshold edits, organisation settings beyond the profile and maturity targets (owner teams, trust-portal exposure, name, industry, engine switches). All rare, all reversible to add.
- **Out:** platform administration, consultant workspace, provisioning and billing, OIDC, catalog import and upgrade, database and queue operations, evidence storage configuration, API-key issuance, membership and invites, organisation create/delete, logo, uploads and downloads, per-user UI preferences, the deprecated DPSIA aliases, the public trust portal.
